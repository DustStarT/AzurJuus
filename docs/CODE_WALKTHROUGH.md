## 一、先把项目理解成四个人各司其职

可以用一个办公室理解这个程序：

- 界面是接待台：接收你说的话，展示人物、消息、任务和成果。
- 调度器是办事登记员：记录谁负责什么、什么时候能开始、遇到问题怎么恢复。
- 模型是会理解语言、提出下一步行动的工作人员。
- 工具网关是实际执行部门：读写文件、运行命令、操作浏览器，并检查权限。

模型不能仅凭一句“我移动了文件”改变磁盘。只有工具网关真的执行移动，磁盘才发生变化。

同样，模型说“完成”也不直接让任务完成。它必须提交证据，应用检查证据，再进入复核。这是项目最重要的设计。

人物头像并不对应五个分别训练的模型。目前主要是同一个云端模型，使用不同人设、方法、上下文和会话。程序没有训练模型权重；所谓成长，目前主要是方法提示、使用记录和候选方法的积累。

## 二、先看哪些文件，暂时不要看哪些

| 阅读顺序 | 文件 | 先理解的内容 |
| --- | --- | --- |
| 1 | `frontend/App.vue` | 点击发送时实际提交什么，消息如何显示 |
| 2 | `backend/run_api.py` | 请求如何变成持久化任务，消息写到哪里 |
| 3 | `backend/run_coordinator.py` | 一个任务从开始到完成的全过程 |
| 4 | `backend/capabilities.py` | 工具到底怎么修改本机，以及权限检查 |
| 5 | `backend/run_store.py` | 任务、调用、事件如何保存和恢复 |
| 6 | `backend/hermes_bridge.py` | 本程序如何和 Hermes 子进程通信 |
| 7 | `backend/collaboration_dialogue.py` | 成员如何边工作边讨论 |
| 8 | `backend/personality.py`、`backend/skill_runtime.py` | 人格表达与方法选择怎样叠加 |
| 9 | `frontend/api.ts`、`frontend/SpeechBubbles.vue` | 实时事件和流式气泡如何接续 |

`backend/services.py` 目前仍然很大，混有数据装配、历史功能和旧流程。第一次阅读不要从第一行读到最后一行。先由 `run_api.py` 中实际调用的方法跳转进去，例如 `_append_message`、`_select_skill_execution`、`_record_skill_run`。

`legacy-test` 是历史兼容测试入口。看到旧流程测试通过，不能据此认定桌面中的新执行链通过。仓库里两种路径同时存在，是当前代码阅读容易混乱的重要原因。

`.vendor/hermes-agent` 是锁定版本的上游代码。多数应用问题应先在桥接、调度、权限和配置层排查，不要一开始就修改上游内部实现。

## 三、一次“整理目录”的请求，完整经过哪里

### 1. 界面提交

`App.vue` 的 `send()` 读取当前会话、输入内容和模式，调用 `/api/messages/send`。

重要字段如下：

| 字段 | 中文意思 | 为什么需要 |
| --- | --- | --- |
| `conversationId` | 当前会话编号 | 决定消息原本属于哪个私聊或群聊 |
| `content` | 用户要求 | 是验收范围的起点 |
| `mode` | 闲聊或任务 | 闲聊没有本地工具授权 |
| `collaborative` | 是否协作 | 决定是否先规划依赖图和建立任务群 |
| `requestId` | 本次提交编号 | 重试同一请求时避免重复派工 |

界面在等待期间禁止同一次发送被重复点击。服务端仍要检查请求编号，因为界面保护挡不住网络重试、重复请求或其他客户端。

### 2. 接口接单

`run_api.py` 的接单函数检查会话是否存在、是否已删除、授权工作区是否有效，然后读取角色和当前设置。

数据库会话在这里短暂打开，只读出需要的数据就关闭。随后等待云端模型时不会一直持有这次数据库事务，否则其他消息、设置保存和后台事件可能被锁住。

私聊历史只保留指挥官和该会话人物的发言。协作结果作为系统背景提供，不能把秘书的口吻当成另一个人物以前说过的话。

### 3. 先保存，再启动

`RunStore.create()` 保存任务，初始状态是排队。`request_key` 有唯一约束；相同编号、相同内容返回原任务，不再创建一份。

相同编号却带不同内容会报错，而不是静默复用错误任务。例如把“列目录”和“删除目录”混成同一个请求，必须拒绝。

用户消息也有稳定编号：任务编号加上固定后缀。因此重复接单不会重复插入同一条用户消息。

### 4. 调度器开始工作

普通任务生成一个主子任务。协作任务先启动秘书规划会话，由秘书调用 `delegate` 提交计划。

计划不是一段看起来像计划的文字，而是包含子任务编号、负责人、目标、前置依赖和验收条件的结构化数据。

### 5. 模型与工具循环

调度器让 `HermesBridge` 启动一个独立进程，并把人设、规则、历史、方法参考、已有证据和当前目标传给它。

模型可以回答文字，也可以提出工具调用。例如要求执行 `list_dir`。Hermes 将这个调用通过工具接入进程送回本机网关。

网关先核对任务令牌、阶段权限、任务状态和参数，再执行真正的 Python 文件操作。结果返回模型，模型据此决定下一步。

这个循环持续到模型给出最终回复、触发中断、遇到错误或者耗尽预算。应用没有用固定五轮限制所有任务。

### 6. 提交与复核

执行者调用 `deliver`，列出成果、验证调用和未解决事项。

应用检查证据后，再启动一个只读复核阶段。复核者读取实际文件，而不是只听执行者说“我检查过了”。

通过后保存最终结果；没有通过则修订。聊天中已经发出的文字与任务是否最终通过，是两种不同状态。

## 四、为什么接入 Hermes，却还自己写调度器

Hermes 解决的是单个执行会话的问题：怎么请求模型、收集工具调用、把结果送回模型、管理上下文和中断。

AzurJuus 要解决的是产品层问题：这个请求属于哪个人物、任务群有哪些成员、谁先做、谁后做、用户在哪里审批、退出后怎么恢复、成果展示在哪里。

如果两层都自由派工，就会出现重复委派、任务状态不同步以及成员互相等待。当前做法是让 AzurJuus 成为唯一的任务调度者，Hermes 负责被安排好的执行会话。

桥接采用标准输入和标准输出上的 JSON-RPC。它可以理解为给子进程发一个带编号的请求，再等相同编号的回应。

`HermesBridge.rpc()` 为请求创建一个等待结果的对象，将请求写入进程输入流。后台读取循环收到回应后，根据编号唤醒对应等待者。模型的流式消息则以事件形式到达，不与普通请求回应混在一起。

这也是为什么不能在标准输出随意打印调试文本：输出流同时承担通信协议。诊断日志需要单独保存。

## 五、任务状态为什么不能只有“进行中”和“完成”

| 状态 | 意义 | 下一步 |
| --- | --- | --- |
| 排队 | 已接收，但未执行 | 等待调度 |
| 执行中 | 正在调用模型或工具 | 继续工作 |
| 等待审批 | 某个具体操作需要确认 | 用户批准或拒绝 |
| 暂停 | 当前轮已停下，保留现场记录 | 核验后继续，或取消 |
| 失败 | 发生明确错误 | 根据错误修复后重试 |
| 取消 | 用户决定不继续 | 不再调度 |
| 完成 | 成果通过验收 | 查看或下载成果 |

子任务还可能是“已提交，待复核”。这不等于最终成功，但也不应立即判为失败。

真实案例：用户只问目录里有什么，模型列出了文件，却把“没有阅读 PDF 正文”记为未解决问题。程序若直接判失败，就把用户没要求的额外工作当成了验收条件。

现在由复核者按原始要求判断：目录清单是否正确。可选深入分析只是备注；真正缺失的用户要求才进入修订。

## 六、交付证据到底怎么检查

`deliver()` 的核心不是检查文字像不像报告，而是检查引用关系。

1. 每条验证引用必须能找到真实工具调用。
2. 调用必须成功，而且属于当前任务的当前执行阶段。
3. 讨论、委派和查询执行日志本身不能冒充对文件的验证。
4. 如果交付文件，必须有当前执行者对该文件的读取记录。
5. 读取时记录的文件摘要必须与交付时的文件摘要一致。
6. 如果还有等待审批或结果不确定的操作，不能完成。

文件摘要使用 SHA-256。可以把它理解成由文件内容计算出的指纹。内容发生变化，指纹通常就会变化。

它能说明“现在的文件与读取时相同”，不能说明“文章逻辑正确”。后者仍需要内容检查、测试程序或模型复核。

因此不要在面试中说“用了哈希就保证任务正确”。更准确的说法是：哈希保证证据与当前文件版本对应，业务正确性由其他验收条件判断。

目录查询可以没有文件产物，但需要实际 `list_dir` 等调用作为证据。不能为了通过系统检查，强迫每个问题都生成一份报告。

### 模型忘记提交怎么办

有时模型已经做完并回答，却漏掉 `deliver`。应用会在同一个会话要求补交，最多两次。

补交阶段只允许读取、搜索和提交证据，不允许再次写入、移动、运行命令或提交网页。这项限制由网关代码检查，不只是写在提示词里。

补交仍失败时，保留原回复并显示错误，不能偷偷替模型编造交付证据。

## 七、协作不是轮流发言：依赖与讨论是两条通道

### 工作依赖

例如：甲整理来源；乙根据甲的来源写报告；丙做另一份独立检查。

正确的关系是乙等甲，丙不必等甲。依赖图表示的是实际成果前提，而不是人物排队顺序。

计划提交后，程序检查负责人是否存在、编号是否重复、依赖是否指向有效节点，并检测循环依赖。例如甲等乙、乙又等甲，这个计划必须拒绝。

当前执行器用 `asyncio.wait(..., FIRST_COMPLETED)` 等待任一正在执行的子任务结束。只要甲完成且有空位，就可以启动乙，无需等同批的丙结束。

测试中专门构造了“丙要等乙开始才结束”的场景，旧的整批等待会卡住，新的调度能推进。这比只检查函数被调用更能证明调度变化有效。

### 人物讨论

`discuss` 是任务内通信工具，参数是目标成员和内容。

执行者发出问题后立刻收到“已排队”，而不是一直等待对方回答。讨论由独立通道运行，最多一个讨论会话并发，执行通道仍最多两个成员。

这避免一种死锁：两个执行名额都被占用，甲等待乙的回复，乙又必须拿到执行名额才能回复。

讨论会话没有文件工具，只能根据已给出的记录提出意见。它不能偷偷在另一个会话里改同一个文件。

问题与回复保存到群聊和任务记录。执行者后续调用工具时会收到新的同伴意见；最终复核前也会等已发起的讨论结束，并读取完整讨论上下文。

讨论每个任务最多八次，每次回复有时间限制。这样既允许争论和纠错，也防止人物互相聊天消耗完执行资源。

这仍不是无限自由的社会模拟。当前没有任意扩张成员、任意重写依赖图的权限；讨论中的建议需要执行者实际采用，才能改变任务产物。

## 八、人物性格在代码里处于什么位置

可以分成三层：

| 层 | 负责什么 | 例子 |
| --- | --- | --- |
| 人设 | 关注点、语气、关系和行为动机 | 喜欢先确认细节，或嫌重复检查麻烦 |
| 方法 | 处理任务的习惯和步骤 | 先整理来源，再归纳，最后检查遗漏 |
| 工具 | 实际允许做哪些事 | 读文件、移动文件、填写网页 |

角色不能通过“我很强势”获得额外工具权限，也不能通过“我比较粗心”绕过最终验收。

`personality.py` 提供共享表达规则，但不统一角色的具体口气。实际人设仍来自角色配置。规则要求不要把设定标签直接念出来，要通过回应方式表现。

例如“我会按照外冷内热、关键词阳光继续说话”是在读提示说明；“嗯，听见了。先坐一会儿？”才是在当前情境里行动。

不要把每个人都写成“先结论、再三条、最后总结”的汇报模板。工作证据已经有专门字段和工作抽屉，聊天不必再次完整复制调用编号与文件指纹。

### 负面性格怎么表现才不空洞

可以是提出少做一次检查、拖着不想开始、对方案不耐烦、因为追求完美重复确认，或者在讨论中暴露疏忽。

同伴需要指出具体影响，例如“你没确认来源，报告会缺依据”，再由执行者修正。最后以文件和证据判断是否完成。

当前没有按概率偷偷删除文件或制造错误的机制。故意破坏磁盘并不能证明人格丰富，只会让工具不可靠。

人物自然度仍依赖模型表现和人设质量。提示规则与一次成功对话不能证明所有人物都已经达到原作表现，需要持续对话样本和人工评价。

## 九、为什么私聊会串入秘书，如何隔离

旧完成回调把秘书的身份和最终正文直接写进原私聊，所以用户在与埃佛森的私聊里看到了能代。

修复后，原私聊只收到系统任务通知。秘书的实际发言保存在协作群，成果在工作记录中查看。

历史记录没有被改写成另一个人说的话。界面对旧的外来角色回传显示中性通知，构造私聊模型历史时也不再把它当作当前人物的过去发言。

这样不仅是修头像，还修了上下文污染。否则即使换了头像，模型仍可能继续沿用秘书的自称和语气。

## 十、流式消息与多个气泡怎样实现

`frontend/api.ts` 接收持久化事件，累计流式文字。每条消息有稳定编号。

`App.vue` 把临时流式数据和数据库消息合并为同一个消息行。数据库接管消息时，不删除原节点再新建。

`SpeechBubbles.vue` 在这个消息行内部显示多个气泡。空行表示角色主动另发一条；特别长的段落才按句子或长度兜底拆分。

拆分边界只依赖前面的文字，后面新到的字不能把已经显示的前几个气泡重新排一遍。代码块也不会被普通句号规则切开。

组件编号使用消息编号，内部气泡使用稳定的顺序编号。因此从流式到完整消息时，仍然是原来的消息和气泡。

界面更新按浏览器绘制帧批量处理事件，避免每来一个字就触发一次完整刷新。网络快照也有请求代次检查，较旧的请求晚返回时不会盖掉新状态。

这解决的是节点连续性与过量更新；不等于任意 GPU 上都已经保证每秒六十帧。性能需要记录设备、窗口尺寸和实际帧时间。

## 十一、数据库为什么不只用一张消息表

当前有三类持久化内容：

- 业务数据库：人物、会话、聊天、设置、动态、方法和成长记录。
- 任务数据库：运行状态、子任务、调用、审批、事件和可检索的成果摘要。
- Hermes 自身会话目录：上游会话与诊断文件。

消息回答“谁说了什么”；调用记录回答“实际做了什么”；任务状态回答“下一步该由谁做”。三者不能互相替代。

数据库事务是一次需要共同成功的读写范围。当前设计避免在等待模型时持有写事务，但两个数据库之间没有一个总事务把所有更新原子提交。

因此需要补投与幂等：任务已经完成、消息还没保存就退出时，重启检查缺失结果消息，按稳定编号补写。

清空工作记录和删除协作群采用归档，保留审计与幂等信息，不删除真实文件。这样清空界面不会让相同请求又被当成新任务执行。

## 十二、暂停、退出、恢复到底恢复了什么

恢复的是持久化目标、历史成果、调用记录和待处理状态，不是把一个 Python 协程的内存直接存进数据库。

如果程序在写文件期间突然结束，磁盘可能已经改变，数据库却还没收到成功回执。此时自动重放可能造成重复移动或重复提交。

应用会把这种结果未知的调用保留下来，暂停任务，要求核验后继续。不能承诺所有外部操作严格只执行一次。

正常退出时，Qt 界面线程不能同步堵住等待后台，否则窗口会显示未响应。后台先取消工具和模型等待，保存状态，再关闭服务和子进程。

正在排队或回复中的讨论被标记中断；重启后不会把没有发生的回复补成成功。

一个真实的启动故障来自相对路径：主程序生成了模型配置，子进程切换工作目录后却去了另一个同名目录。修复是启动前锚定绝对路径，并用真实批处理入口验证，不能只依赖绝对路径测试夹具。

## 十三、朋友圈怎样运行，为什么它会被任务打断

`idle_social.py` 选择到期的角色，读取近期记忆与关系，生成动态，再选择回应者。

生成过程不跨网络请求保持数据库会话。新任务开始时，低优先级社交生成可以被取消，避免把模型请求和本机资源长期占住。

动态和评论使用同一套人物表达原则，但它们不是任务验收记录。角色说“今天忙坏了”不能证明某项文件任务完成。

当前朋友圈更接近“带关系和时间调度的角色社交生成”，还不是持续独立生活的模拟世界。任务经历与长期关系的精细演变仍需要进一步连接和评价。

本轮已补上一个明确连接：验收成功后，每位实际执行成员的成果摘要写入业务记忆，绑定源任务编号。社交生成读取近期记忆时便能参考这些经历。稳定编号防止重复写入；失败任务、没有执行工作的旁观者和单纯讨论不会因此获得“已完成工作”的记忆。这里保存的是摘要，不是把整个工具日志塞进朋友圈提示。

## 十四、技能选择和学习到底有多“智能”

当前方法选择在 `skill_runtime.py`：按模式选公有方法，再按角色私有方法的标签、适用模式和置信分数选择补充方法，拼接成参考提示。

这不是模型从无限技能库中自主搜索，也不是强化学习。不要在项目介绍里混淆这些概念。

成功任务写入方法使用记录，包含选用方法、阶段和实际工具。通过协作依赖交接可以产生私有候选；候选带来源任务，默认不启用。

“方法与成长”面板可以查看已启用方法、候选说明、最近使用记录和启发来源。

候选多次试用、与旧方法对比、成熟后晋升的完整机制还没实现。当前不能因为看见一条候选记录，就说角色已经学会了新技能。

公有方法修改还需要秘书审查、用户确认、版本差异和回滚。旧提案接口存在，但不代表新的完整治理界面已经完成。

## 十五、你以后修改代码，可以按这个方式控制范围

### 想改人物说话

先改具体角色的人设，再检查 `personality.py` 是否存在压过人物差异的统一格式要求。不要先改文件工具。

测试至少包含日常问候、被追问、意见分歧、任务完成、犯错后纠正。只看一次“你好”无法评价人格稳定性。

### 想加一个工具

需要同时考虑工具目录、实际实现、阶段权限、审批原因、输出结构、失败处理和回归测试。

只把名称写入工具目录会让模型看见一个实际上不能执行的能力；只写实现却不配置权限，也可能造成越权入口。

### 想改协作顺序

先决定是依赖变化还是成员讨论。依赖变化要修改结构化计划与状态；讨论只提出意见，不自动改动依赖。

测试要构造交错完成、一个成员失败、任务取消和共享写入冲突，不只测试甲做完后乙做完的理想场景。

### 想修界面闪烁

先检查节点编号、条件渲染和快照覆盖次序，再看动画。删除一个节点再用动画把新节点淡入，不能解决原来的数据交接问题。

### 不知道从哪里查故障

| 现象 | 先查什么 |
| --- | --- |
| 发送后没有任务 | 接单接口返回值、模式、会话是否已归档 |
| 任务存在但没回复 | 运行阶段、桥接日志、模型配置、子进程目录 |
| 有文字但没文件 | 工具调用是否真的成功、是否只有进度回复 |
| 文件正确却失败 | 交付字段、当前阶段证据、未解决事项是否扩大范围 |
| 出现其他人物口吻 | 消息署名、私聊历史过滤、是否直接转贴秘书正文 |
| 群成员互相等待 | 工作依赖和讨论等待是否占用同一个执行名额 |
| 关闭未响应 | GUI 是否同步等待、审批 HTTP 是否先被取消 |
| 一刷新消息消失 | 稳定编号、消息是否持久化、旧快照是否覆盖新状态 |

## 十六、面试时怎样讲实现，而不是只报技术名词

“我用了异步”太宽泛。可以说：模型请求等待期间关闭数据库事务；工作通道最多两个成员；任一成员结束后立即推进已满足的依赖；讨论有独立并发额度，避免等待对方回复时占满工作名额。

“我做了可靠性”也太宽泛。可以说：请求编号防止重复接单，调用编号防止重复处理已知调用；外部副作用结果未知时暂停核验；结果消息通过稳定编号补投，但不承诺跨数据库和网页提交的全局原子性。

“我做了多人格”应当解释三件事：角色自己的设定、上下文身份隔离、方法与工具权限分离。再展示两个人对同一个具体问题的不同关注点，比展示两个头像更有说服力。

“我做了学习”目前应当说：保存经验证的任务使用记录，并生成可追溯的私有方法候选。完整多次试用与晋升还未实现，不能宣称自主训练。

这几个具体解释，才是你能把控这个项目的标志。先沿一条请求读懂生产执行链，再扩展到社交和成长，没必要一次记住仓库所有旧代码。
