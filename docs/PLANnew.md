# AzurJuus 聊天终端体验重构计划

## 一、目标与已确认方向

采用**独立表达层、精致游戏聊天终端、原作背景与轻度日常**。普通发言通常为 **1–2 个短气泡、合计约 30–120 字**；协作群保留成员完整的主动讨论，但不把工具日志和例行核验当成角色聊天。

本轮解决四个具体问题：

- 执行报告直接进入聊天，造成长篇、重复、审计式发言。
- 角色使用动作旁白，错误地把聊天终端演成面对面场景。
- 人设、关系、台词情境及实际生效版本混杂。
- 界面泛白、层级模糊、装饰文字过多，消息节奏与动画缺乏统一控制。

保持 Hermes 执行核心、现有权限与验收机制，不通过降低工作可靠性换取角色感。人工评价通过前，不宣称“人格自然度已解决”。

## 二、执行与角色表达分离

### 独立表达链

- Hermes 的计划、执行说明、工具结果和审查报告进入工作记录，停止直接作为聊天消息发布。
- 新增无工具权限的表达服务，接收“谁对谁说、说话目的、可公开事实、当前关系、最近对话”，生成角色短消息。
- 普通闲聊直接使用表达服务，不先经过一次执行模型调用。任务阶段仅在需要交流、交付结果或处理问题时增加表达调用。
- 表达服务不接收完整工具流水、权限长文和交付格式说明。用户追问过程时，按当前任务关联读取必要证据，生成详细回答。
- 私聊始终由对应人物发言；协作群保留每个成员的主动提问、回应、异议、解释和纠错。表达层不得篡改讨论观点或擅自宣布问题已经解决。

### 消息契约与可靠性

新增持久化表达队列，消息包含稳定标识、人物、接收对象、关联任务、来源事件、表达意图、分段正文和投递状态，继续使用现有事件通道。

- 同一来源事件重放不重复发言；不同成员的真实讨论不因内容接近而被合并。
- 普通任务发言以 30–120 字为目标，校验上限为 180 字、最多三个气泡；明确要求详细解释、代码或报告时解除短消息限制。
- 先生成并检查完整短消息，再逐段呈现。检查身份、动作旁白、长度、来源引用及明显的数字和路径矛盾；不依赖前端截断或删除括号。
- 不合格结果最多修订一次。表达失败时显示真实状态卡片，不回退展示整篇执行报告，也不把成功任务改成失败。
- 表达等待可取消，默认超时 15 秒；前台闲聊优先于任务表达，后台社交最低优先级。记录新增调用次数、耗时和费用。
- 旧聊天原文保留；旧式长篇任务报告在界面折叠为“历史工作回复”，不删除、不重新配音式播放，也不继续作为新回复的风格示例。

## 三、角色卡、世界书与社会关系

借鉴 SillyTavern 的[角色卡与对话示例](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)、[世界书](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)和[提示编排](https://docs.sillytavern.app/usage/prompts/prompt-manager/)，实现适合聊天终端的背景组织方式；不引入其完整运行时，也不照搬小说式扮演示例。

### 材料整理与生效管理

- 首批覆盖现有五名角色、所属阵营及有明确关联的人物；关联人物可以只是背景条目，不自动成为执行成员。
- 以游戏台词、剧情为主要依据，Wiki 作为可追溯资料载体。保存出处、章节或台词情境、核对日期，区分原作事实、作者解释和用户设定。
- 清理署名、网页杂项、皮肤台词混用等问题；陌生、友好、恋爱、誓约及特殊场景台词分别标记，不默认启用高亲密关系。
- 统一角色材料的版本与导入流程：本地材料形成版本化基础卡，数据库保存启用版本及用户覆盖。界面显示“当前生效版本”，支持查看差异、应用更新和恢复基础版本；不静默覆盖用户人设。
- 每个角色补充六组原创的终端对话示例：普通招呼、简短回应、任务确认、求助、分歧、承认错误。示例用于表现差异，不要求模型照背。

### 世界设定与信息边界

上下文按固定顺序组装：**终端规则 → 当前角色 → 对话对象与关系 → 相关世界条目 → 可见经历 → 最近对话及本次说话意图**。

- 全局明确这是远程文字聊天终端。禁止括号动作、第三人称旁白和替用户描写动作；允许“我刚泡了茶”这样的文字分享，但不能声称用户已经接过或喝过。
- 允许符合设定的轻度个人日常，不启动离线剧情模拟；虚构日常单独标记，不能成为文件任务证据，也不能自动成为未参与人物的共同记忆。
- 世界书按人物、阵营、地点、话题和台词适用情境检索；默认最多六条，约 1,200 token。公共世界背景可以共享，私人判断仍按人物隔离。
- 关系拆成“原作背景、用户覆盖、应用内经历”。同阵营不自动等于亲密，共同任务不自动等于能力可信；没有出处的直接关系保持未知。
- 原作关系与应用中的关系变化同时保留。关系实际影响称呼、解释多少、向谁求助和怎样提出异议，而不是要求每次口头复述关系。

新增只面向本地用户的角色版本、世界条目和提示预览管理接口；扩展现有关系接口返回来源类型及证据。调试预览不包含密钥，也不开放为角色工具。

## 四、JUUS 视觉与消息节奏

### 视觉重设计

采用青蓝导航、角色立绘与浅色消息面的原作方向，调整为更紧凑、有层次的桌面聊天终端：

- 标准桌面导航宽约 76px，会话列表 300–340px；会话行约 84–96px，头像约 52px，把主要空间留给聊天。
- 减少全屏泛白蒙层；背景保留角色辨识度，文字所在区域使用稳定、足够不透明的阅读面。
- 统一字号、间距、圆角和阴影层级。正文默认 15px，气泡宽度限制约 36 个中文字符，避免跨屏长行。
- 删除重复栏目标题、英文装饰标签、常驻宣传语和无作用的说明；图标保留悬停提示与无障碍名称。异常、审批和任务状态仍有明确入口。
- 朋友圈沿用横向大卡片和左图右文详情；工作抽屉减少常驻说明，详细过程按需展开。
- 本地原始截图和视频目前未检索到，先使用既有会话参考图、现存展示截图及 JUUS 视觉约定，不因此阻断设计。

### 动效与投递

遵循 [Fluent](https://fluent2.microsoft.design/motion) 与 [Apple](https://developer.apple.com/design/human-interface-guidelines/motion) 强调的短促、有用途、可中断原则，具体时长作为本项目设计参数：

- 按钮反馈 120ms，气泡进入 180ms，抽屉进入 220ms、退出 160ms；主要使用透明度与不超过 6px 的位移。
- 首个气泡准备好后立即显示；后续气泡间隔按前一段长度计算，限制在 450–1,000ms。提供即时、自然、舒缓三档，默认自然。
- 同一会话使用统一呈现队列，避免多名成员同时喷出消息。审批、失败和停止状态不等待动画队列。
- 后端仍实时保存消息；动画只控制展示。切换会话、重连和加载历史不重播已显示内容。
- 长报告不逐句慢放，以摘要加展开呈现；普通消息等待队列提供“立即显示”入口。
- 减少动态效果关闭位移与淡入；保留跟随底部、向上阅读不拉回、中文输入与选区稳定。

先完成私聊、群聊、朋友圈、工作抽屉四类真实数据页面，再统一处理设置与人物详情，避免只美化空白样例。

## 五、实施顺序与验收

1. **建立真实基线**：只读抽取近期普通聊天和任务片段，脱敏后建立固定场景；记录长度、重复内容、动作旁白、错误身份和额外确认次数。
2. **重整人物材料与提示生效链**：完成五人角色卡、关系来源、世界条目及版本管理，检查当前数据库与本地文件的差异。
3. **接入独立表达层**：完成消息队列、来源关联、短消息校验和故障降级，再接入闲聊、任务、讨论和朋友圈。
4. **重建视觉与投递节奏**：完成四类核心页面、统一动效和消息播放状态。
5. **验收与文档**：更新中文代码讲解，提供当前生效提示检查方法、真实前后对照和剩余限制。

验收要求：

- 固定场景中不出现动作旁白、替用户行动、跨角色私聊或虚构工具结果；正确保留技术文本中合法的括号。
- 默认任务短消息至少 90% 不超过 120 字，全部满足 180 字校验上限；详细回答场景单独统计。
- 验证每段协作发言都有真实来源，完整主动讨论不丢失，重复事件不重复投递；表达失败不影响执行成果。
- 验证背景检索、亲密情境限制、关系方向、用户覆盖优先级、私人信息边界和版本回退。
- Playwright 覆盖并发消息、断线恢复、历史加载、立即显示、输入法、滚动位置和减少动态效果；通过实际桌面入口检查布局与退出。
- 覆盖 1280×720、1600×900、1920×1080，以及 100%、125%、150% 缩放；记录帧时间、长任务和云端等待，不能用节点稳定替代流畅度测量。
- 先运行 12 个代表场景的小规模真实模型对照，再扩展至完整人格场景集；输出匿名前后样例，邀请用户及另一名评阅者评价自然度和角色辨识。程序验证与人工评价分别报告。
- 新表达链使用统一开关上线，旧记录和用户修改保留，回退不丢数据。
